## 왜 프롬프트가 중요한가?

### 같은 AI, 같은 질문 → 10배 차이

```
❌ 나쁜 프롬프트
"회의록 정리해줘"
→ AI: "네, 회의록을 정리해드리겠습니다. 회의 내용을 알려주시면..."

✅ 좋은 프롬프트
"아래 회의록에서 결정사항, 액션아이템(담당자·기한), 다음 안건을
표 형식으로 분리해줘. 한국어. 3줄 요약도 최상단에."
→ AI: [즉시 원하는 형식으로 정리된 결과물 출력]

```

> 💡 프롬프트 품질 향상 = 개발 비용 절감 + 서비스 품질 향상

## 2-1 | RCIF 프레임워크란?

### 4가지 요소로 완성하는 프롬프트

| 요소 영문 역할 예시  |             |           |                         |
| ------------ | ----------- | --------- | ----------------------- |
| **R**        | Role        | 전문가 역할 부여 | “당신은 10년 경력 IT 컨설턴트입니다” |
| **C**        | Context     | 상황·배경 제공  | “제조업 ERP 도입 검토 중이며…”    |
| **I**        | Instruction | 동사로 명확히   | “리스크 3가지를 분석하세요”        |
| **F**        | Format      | 출력 형태 지정  | “번호 목록, 각 항목 2문장 이내”    |

---

## 2-1 | RCIF 비유

> 💡 **비유 ①: 프롬프트는 “직원 업무 지시서”입니다**
>
> “자료 정리해줘” (나쁨)
>
> vs
>
> “3월 고객 상담 기록을 고객사별로 분류하고,
>
> TOP 3 문의 유형을 표로 오늘 5시까지 정리해줘” (좋음)
>
> **이 비유의 한계**: 직원은 되물을 수 있지만
>
> AI는 질문 없이 추측으로 답합니다. 더 구체적이어야 합니다.

> 💡 **비유 ②: 프롬프트는 “요리 레시피”입니다**
>
> “맛있는 파스타” → 레시피가 아닙니다
>
> “4인분, 까르보나라, 크림 없이, 10분 안에” → 재료·방식·제약이 있는 레시피
>
> **이 비유의 한계**: 레시피와 달리 프롬프트는 temperature에 따라
>
> 결과가 매번 조금씩 달라질 수 있습니다.

## 2-1 | RCIF 코드 비교

```
# rcif_comparison.py
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage  # 역할별 메시지 타입

load_dotenv()                                           # .env에서 API 키 로드
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)   # temperature=0: 일관된 출력

meeting_text = """
박팀장: 신제품 출시를 8월 15일로 확정하자고 제안합니다.
김팀장: 동의합니다. 마케팅은 SNS 먼저 시작하고요.
이팀장: AI 추천 기능은 9월 적용하겠습니다. 개발 일정 필요해요.
"""

# ❌ RCIF 없음 — AI가 정리 형식을 임의로 선택
bad = llm.invoke(f"회의록 정리해줘:\n{meeting_text}")
print("=== RCIF 없음 ===")
print(bad.content)
# 예상 출력: "신제품 출시는 8월 15일로 결정되었습니다. 마케팅팀은..."
# (형식 없음, 길이 불규칙, 요청한 구조 없음)

# ✅ RCIF 적용 — 역할·배경·지시·형식을 명확히 전달
good = llm.invoke([
    SystemMessage(content="[R] 당신은 비즈니스 커뮤니케이션 전문가입니다."),
    # SystemMessage: AI의 전반적 역할과 행동 원칙 설정
    HumanMessage(content=f"""[C] 킥오프 회의 기록입니다.
{meeting_text}

[I] 아래 형식으로 정리해주세요.
[F]
1. 핵심 결정 사항 (번호 목록)
2. 액션 아이템 표: 담당자 | 내용 | 기한
3. 다음 회의 안건"""),
    # HumanMessage: 실제 사용자 입력 (배경 + 지시 + 형식)
])
print("\n=== RCIF 적용 ===")
print(good.content)
# 예상 출력:
# 1. 핵심 결정 사항
#    1) 신제품 출시일 8월 15일 확정
#    2) 마케팅: SNS 채널 우선 시작
# 2. 액션 아이템
#    | 담당자 | 내용               | 기한 |
#    | 이팀장 | 개발 일정 공유     | 미정 |
# 3. 다음 회의 안건
#    - AI 추천 기능 개발 일정 확인

```

> ⚠️ **흔한 실수: Role(역할)이 지나치게 추상적**
>
> ❌ `"당신은 전문가입니다"` — AI가 어떤 분야 전문가인지 추측해야 합니다.
>
> ✅ `"당신은 법무팀에서 10년 근무한 IT 계약 검토 전문가입니다"` — 역할이 구체적일수록 일관된 출력이 나옵니다.
>
> RCIF 4요소 중 하나라도 빠지면 AI가 임의로 채웁니다. 결과가 이상하면 어떤 요소가 빠졌는지 먼저 확인하세요.

## 2-2 | 두 가지 프롬프트 전략

### 왜 두 전략이 필요한가?

단순한 분류는 설명 없이도 AI가 잘 처리하지만, 기업 내부 도메인 용어나 특수한 분류 기준은 예시를 보여줘야 AI가 정확하게 따릅니다. 두 전략의 차이를 알면 **토큰(비용)과 정확도** 사이에서 상황에 맞는 선택을 할 수 있습니다.

### Zero-shot과 Few-shot의 차이

> 💡 **비유 ①: 신입에게 업무를 지시하는 두 방법**
>
> **Zero-shot**: “이 민원을 유형별로 분류해줘”
>
> → AI가 훈련된 지식으로 스스로 판단
>
> **Few-shot**: “이 예시처럼 분류해줘:
>
> ・ ‘배송 안 됐어요’ → 배송문의
>
> ・ ‘화면이 깨졌어요’ → 제품불량
>
> ・ ‘환불하고 싶어요’ → 환불
>
> 이제 ’다음 달 주문한 노트북이 안 왔어요’를 분류해줘”
>
> → 패턴을 모방
>
> **이 비유의 한계**: 신입은 경험이 쌓이지만,
>
> AI는 Few-shot 예시를 세션 밖으로 기억하지 않습니다.

> 💡 **비유 ②: Zero-shot은 “경험자에게 맡기기”, Few-shot은 “표준 매뉴얼 주기”입니다**
>
> 경험 많은 직원(Zero-shot)은 “민원 분류해줘”라고 하면 알아서 처리합니다.
>
> 하지만 우리 회사만의 특수한 분류 기준이 있다면, 신규 직원에게 “이 예시를 봐”라며 SOP 매뉴얼(Few-shot)을 줘야 합니다.
>
> 도메인 분류 기준이 일반적이지 않을수록 Few-shot이 더 효과적입니다.
>
> **이 비유의 한계**: 실제 직원은 매뉴얼 없이도 점점 나아지지만, AI는 Few-shot 예시를 세션 밖에서 학습하지 않습니다.

---

## 2-2 | 언제 어떤 전략을?

### 선택 기준

| 상황 권장 전략 이유     |           |                   |
| --------------- | --------- | ----------------- |
| 간단한 분류 (3가지 이하) | Zero-shot | 예시 없어도 충분         |
| 복잡한 기준 필요       | Few-shot  | 패턴 명시 필요          |
| 특수한 도메인 용어      | Few-shot  | AI가 모르는 맥락 전달     |
| 토큰·비용이 중요       | Zero-shot | Few-shot은 토큰 소비 ↑ |
| 일관된 포맷 필요       | Few-shot  | 출력 형식 고정          |

> ⚠️ **흔한 실수: Few-shot 예시의 출력 포맷이 원하는 결과와 불일치**
>
> 예시 출력: `'배송 안 됐어요' → '배송문의입니다. 처리 기한은 3일입니다.'`
>
> 실제 원하는 출력: `배송문의` (카테고리 이름만)
>
> → AI가 설명까지 추가로 출력하는 현상 발생.
>
> 해결: 예시의 출력 형식을 **원하는 최종 출력과 정확히 일치**시키세요.

## 2-2 | 코드 비교

```
# shot_comparison.py
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

load_dotenv()                                           # .env에서 API 키 로드
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)   # temperature=0: 재현 가능한 결과

inquiry = "지난달 주문한 노트북이 아직 안 왔어요."

# Zero-shot — 예시 없이 AI가 훈련된 지식으로 판단
zero = llm.invoke(
    f"고객 문의를 분류해. 분류: [배송문의, 환불, 제품불량, 기타]\n"
    f"문의: '{inquiry}'\n"
    f"분류 결과만 출력:"
)
print("Zero-shot:", zero.content)
# 예상 출력: "배송문의"

# Few-shot — 예시 3개로 패턴을 명확히 제시
few = llm.invoke(
    f"고객 문의를 분류해. 분류: [배송문의, 환불, 제품불량, 기타]\n\n"
    f"예시:\n"
    f"'주문 2주 됐는데 배송 안 됐어요.' → 배송문의\n"     # 예시: 배송 지연
    f"'화면에 금이 가 있어요.' → 제품불량\n"              # 예시: 물리적 파손
    f"'환불하고 싶어요.' → 환불\n\n"                      # 예시: 환불 요청
    f"분류할 문의: '{inquiry}'\n"
    f"분류 결과만 출력:"
)
print("Few-shot:", few.content)
# 예상 출력: "배송문의"  (동일 결과이지만 복잡한 케이스에서 차이 발생)

```

### 📚 강의 교안

## 2-3 | Prompt Iteration이란?

### 왜 한 번에 좋은 프롬프트를 만들 수 없는가?

첫 번째 프롬프트가 완벽한 경우는 드뭅니다. 프롬프트 개선은 **“작성 → 테스트 → 관찰 → 수정”** 의 반복입니다. 중요한 것은 각 버전을 LangSmith에 남겨두고 비교하는 것입니다 — 버전 기록이 없으면 “어느 게 더 나은지” 기억에만 의존하게 됩니다.

### 프롬프트는 A/B 테스트입니다

> 💡 **비유 ①: 프롬프트 개선은 “광고 A/B 테스트”입니다**
>
> 광고 문구를 버전별로 테스트해 클릭률 높은 것을 고르듯,
>
> 버전별 결과를 LangSmith에 기록·비교합니다.
>
> **이 비유의 한계**: A/B 테스트는 통계적 유의성이 핵심이지만,
>
> 프롬프트는 **품질 판단 기준을 미리 정하는 것**이 더 중요합니다.

> 💡 **비유 ②: 프롬프트 개선은 “글쓰기 퇴고”입니다**
>
> 첫 초안은 생각을 일단 쏟아내고(v1), 두 번째에는 형식을 잡고(v2), 세 번째에는 독자를 의식해 다듬습니다(v3).
>
> 같은 내용이라도 독자(여기서는 AI)에게 맞게 조율할수록 원하는 결과가 나옵니다.
>
> **이 비유의 한계**: 글쓰기 퇴고는 정답이 없지만, 프롬프트 개선은 LangSmith 비교라는 객관적 근거가 있습니다.

### 반복 개선의 핵심 원칙

```
v1 → 최소 동작 확인
v2 → 형식·구조 추가
v3 → 역할·독자·제약 추가
v4 → 에지 케이스 처리  ← ⭐ 심화 실습 대상

```

## 2-3 | v1 → v2 → v3 코드

```
# v1 — 최소 동작: 일단 요약이 되는지 확인
v1 = llm.invoke(f"이메일 요약:\n{email}")
print("=== v1 ==="); print(v1.content)
# 예상 출력: "이 이메일은 8/10 2시 미팅을 요청하는 내용입니다."
# 문제: 너무 길고, 임원이 판단하기 어려운 형식

# v2 — 형식 지정: 원하는 필드 구조 추가
v2 = llm.invoke(
    f"아래 형식으로 이메일 요약:\n"
    f"- 발신자:\n"
    f"- 핵심 요청:\n"
    f"- 시급성:\n"
    f"\n이메일:\n{email}"
)
print("=== v2 ==="); print(v2.content)
# 예상 출력: "발신자: 박철수 / 핵심 요청: 미팅 요청 / 시급성: 보통"
# 개선: 포맷 생김. 문제: 시급성 판단 기준 없어 AI마다 다르게 판단

# v3 — 역할 + 독자 + 제약: 누가 읽는지, 어떤 판단을 내려야 하는지 명시
v3 = llm.invoke(
    f"바쁜 임원 보고 관점으로 이메일을 요약해.\n"
    f"형식:\n"
    f"- 이름:\n"
    f"- 핵심 요청 (20자 이내):\n"
    f"- 필요 조치 (즉시처리/검토필요/참고):\n"
    f"- 기한:\n"
    f"\n이메일:\n{email}"
)
print("=== v3 ==="); print(v3.content)
# 예상 출력:
# 이름: 박철수
# 핵심 요청: 8/10 AI미팅 참석요청 (14자)
# 필요 조치: 검토필요
# 기한: 8/10 이전 답변 필요

```

## 2-4 | PromptTemplate 비유

> 💡 **비유 ①: PromptTemplate은 “빈칸 있는 공문서 양식”입니다**
>
> 빈칸(`{변수}`)만 채우면 되는 양식.
>
> `{industry}`, `{tone}` 자리가 있는 프롬프트입니다.
>
> **이 비유의 한계**: 공문서 양식은 수정이 어렵지만
>
> 템플릿은 변수만 바꾸면 즉시 다른 프롬프트가 됩니다.

> 💡 **비유 ②: ChatPromptTemplate은 “콜센터 응대 스크립트”입니다**
>
> System(응대 원칙)과 Human(고객 입력) 두 역할로 나뉜 스크립트에
>
> `{이름}`, `{제품명}`만 채웁니다.
>
> **이 비유의 한계**: 콜센터 스크립트는 사람이 읽지만 이것은 AI가 읽습니다.

## 2-4 | ChatPromptTemplate 코드

```
# prompt_template.py
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv

load_dotenv()
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 템플릿 정의 — {중괄호}가 변수 자리 (단일 중괄호 사용!)
chat_template = ChatPromptTemplate.from_messages([
    ("system", "당신은{industry} 산업 전문 분석가입니다.{tone} 어조로 한국어로 답하세요."),
    ("human", "{task}에 대해{format}으로 분석해주세요."),
])

# 변수를 채워서 호출
chain = chat_template | llm   # 내일 LCEL에서 자세히 배울 연결 방식!
                               # chat_template 출력이 llm 입력으로 자동 전달

result = chain.invoke({
    "industry": "제조업",
    "tone": "전문적이고 간결한",
    "task": "ERP 도입 리스크",
    "format": "번호 목록 3가지",
})

# parser 없이 template | llm 이면 결과가 AIMessage 객체 → .content로 텍스트 추출
# Day 3에서 StrOutputParser()를 추가하면 result가 바로 str이 되어 .content 불필요
print(result.content)
# 예상 출력:
# 1. 데이터 마이그레이션 복잡성: 기존 시스템의 데이터를 ERP로 이전하는 과정에서...
# 2. 변경 관리 부담: 사용자들의 새 시스템 적응 교육 및 저항 관리...
# 3. 시스템 통합 리스크: 기존 설비·SCM·MES 시스템과의 연동...

```

> ⚠️ **흔한 실수 1: 변수명 불일치 → KeyError**
>
> 템플릿에 `{industry}`라고 쓰고 `invoke({"industy": "제조업"})` 처럼 오타가 나면:
>
> `KeyError: 'industry'` 에러 발생.
>
> 해결: 템플릿의 `{변수명}`과 `invoke()` 딕셔너리 키를 **완전히 동일하게** 작성하세요.

> ⚠️ **흔한 실수 2: 이중 중괄호 사용** **`{{변수}}`**
>
> LangChain 템플릿은 단일 중괄호 `{변수}`를 씁니다.
>
> 이중 중괄호 `{{변수}}`를 쓰면 변수로 인식되지 않고 `{변수}` 텍스트가 그대로 출력됩니다.
>
> (에러는 나지 않고 조용히 잘못된 결과가 나옵니다 — 가장 찾기 어려운 버그 유형)

examples = [

final_template = ChatPromptTemplate.from_messages([

### 🏋️ 실습 자료

## 2-5 | 실습 단계별 가이드

### Step 1: 시스템 프롬프트 v1 작성

> ℹ️ 아래 스켈레톤 코드의 `[역할]`, `[배경·상황]` 등은 \*\*여러분이 직접 채워야 하는 자리(placeholder)\*\*입니다. 대괄호`[]` 안의 내용을 실제 내 서비스에 맞는 내용으로 교체하세요. 그대로 실행하면 AI가 이상한 결과를 냅니다.

```
# my_service_prompt_v1.py  ← Day 1의 my_service_v1.py를 프롬프트 템플릿으로 발전
# Day 1의 system_prompt 문자열 변수를 이 파일의 ChatPromptTemplate으로 교체합니다.
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv

load_dotenv()
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# ① RCIF 요소를 각각 채워보세요 — [대괄호] 안을 내 서비스 내용으로 교체
role        = "당신은 [역할 — 예: 회의 기록 전문가]입니다."
context     = "[배경·상황 — 예: 주어진 텍스트는 IT 프로젝트 회의 내용입니다]"
instruction = "[동사로 시작하는 명령 — 예: 핵심 결정사항을 추출하여 정리하세요]"
output_format = "[출력 형식 — 예: 결정사항: / 담당자: / 기한:]"   # 변수명 output_format 사용 권장

system_prompt = f"{role}\n{context}\n{instruction}\n{output_format}"

# ② ChatPromptTemplate으로 구현
template = ChatPromptTemplate.from_messages([
    ("system", system_prompt),
    ("human", "{user_input}"),  # 내 서비스에 맞는 변수명으로 변경 가능
])

# ③ LLM과 연결
chain = template | llm

# ④ 테스트 실행
result = chain.invoke({"user_input": "여기에 테스트 입력을 넣으세요"})
print(result.content)

```

> ⚠️ **흔한 실수**: 스켈레톤의 `[대괄호]` 안 텍스트를 교체하지 않고 그대로 실행하면,
>  AI가 “[역할]”이라는 단어 자체를 역할명으로 인식해 엉뚱한 결과가 나옵니다.
>  대괄호 안을 내 서비스 실제 내용으로 반드시 교체한 뒤 실행하세요.

### Step 2: 테스트 3케이스 실행

정상 케이스 / 엣지 케이스 / 빈값 처리 각 1개씩

| 케이스 설명 목적  |                 |          |
| ---------- | --------------- | -------- |
| **정상 케이스** | 전형적인 입력         | 기본 동작 확인 |
| **엣지 케이스** | 짧거나 불완전한 입력     | 예외 처리 확인 |
| **비정상 입력** | 빈 문자열 또는 무관한 내용 | 실패 패턴 발견 |

### Step 3: v2 개선

v1 실행 결과를 보고 아래 체크리스트로 문제를 찾아 v2에서 수정하세요:

| 점검 항목 확인 방법     |                                 |
| --------------- | ------------------------------- |
| Role이 너무 추상적인가? | “전문가” → “○○ 분야 ○년 경력” 구체화       |
| Format이 있는가?    | 출력에 구조가 없으면 Format [F] 추가       |
| 출력 길이가 맞는가?     | 너무 길면 “○줄 이내” 제약 추가             |
| 필드가 빠졌는가?       | 원하는 정보가 출력에 없으면 Instruction에 추가 |

v2 작성 후 LangSmith에서 v1 vs v2 비교 트레이스를 확인하고, 개선점 1문단을 슬랙에 공유하세요.
